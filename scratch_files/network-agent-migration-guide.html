Confirm the wording with product before publishing, because it describes unreleased features.
Checked against the agent
Every command was checked against newrelic-forks/newrelic-network-agent. All documented flags still exist. With the old /etc/ktranslate paths in snmp-base.yaml, every container type exits at startup and restarts in a loop. Inside the container, traps and syslog listen on ports 1620 and 5143. Device entities are unaffected, because the entity rules key on values that don't change. The device check in step 6 uses fields the agent puts on every device's data: device_name, collector.name, and tags.container_service (set from -service_name). Syslog messages carry tags.container_service only for devices listed in snmp-base.yaml, which is why the syslog variant filters on plugin.type instead. The provider != 'kentik-agent' line drops the agent's heartbeat metrics, whose device_name is the container's hostname (on Docker's default network, the container ID), so it changes when the container is re-created. The steps stop the old container before the paths change because kTranslate can't load profiles from /etc/network-agent and crash-loops if it restarts with the edited file. Discovery doesn't undo the edit: both agents re-read the file's global section right before they save discovered devices. The new image has no /etc/ktranslate folder, so any flag or mount that points there has to change.
Open before publishing
  1. The built-in ktranslate-health log parsing rule expects log lines that start with "ktranslate". The new agent's lines start with "network-agent", so they arrive unparsed, with no severity or container_service. The Logs team needs to update the rule. Until then, the "Find the agent's logs" section promises only that filters on logtype and plugin.type keep working; don't extend that to severity.
  2. The guided install in the New Relic UI still generates kentik/ktranslate, Podman, and Linux package commands.
  3. newrelic/network-agent:latest has to exist at release. Docker Hub only has release-candidate tags today.

Migrate from kTranslate to the New Relic Network Agent

New Relic now builds, publishes, and supports the agent that collects your network data. The New Relic Network Agent replaces the kTranslate container image, and it's the first step toward upcoming improvements to network monitoring. Future fixes and improvements ship only in the New Relic Network Agent. For each container, you update two paths in its configuration file, then re-create the container with the new image.

important

Action required. Migrate your deployments to the New Relic Network Agent by [DEADLINE DATE]. After that date, New Relic supports only deployments that use the newrelic/network-agent image.

tip

What's coming. New Relic is building tools to manage your network agents from the New Relic UI: discover devices and choose what to monitor, spread monitoring across containers automatically, and see the health of all your agents in one place. These capabilities will work only with the New Relic Network Agent, so by migrating now you can start using them as soon as they're available.

Docker

What stays the same: your devices keep their entities and history, and metric names don't change. Your license key, account ID, region, and environment variables such as KENTIK_MERAKI_API_KEY carry over as they are, and so do your docker run flags, apart from any path under /etc/ktranslate. Only queries that filter on collector.name or on agent log text need updates. For details, see Update queries, alerts, and dashboards.

Before you begin

  1. On each Docker host, list your kTranslate containers:

    docker ps -a --format "{{.ID}}  {{.Names}}  {{.Image}}" | grep ktranslate

    Output example:

    3297b134a352  ktranslate-snmp   kentik/ktranslate:v2
4962a854b386  ktranslate-sflow  kentik/ktranslate:v2

  2. Note the settings each container was started with. If you no longer have the original docker run command, docker inspect shows them:

    # Flags passed after the image name
docker inspect --format '{{json .Config.Cmd}}' $CONTAINER_NAME
# Environment variables (this includes your license key, so don't share the output)
docker inspect --format '{{json .Config.Env}}' $CONTAINER_NAME
# Files mounted into the container, such as snmp-base.yaml
docker inspect --format '{{json .HostConfig.Binds}}' $CONTAINER_NAME
# Published ports, network mode, and restart policy
docker inspect --format '{{json .HostConfig.PortBindings}} {{.HostConfig.NetworkMode}} {{.HostConfig.RestartPolicy.Name}}' $CONTAINER_NAME

  3. Back up each snmp-base.yaml file before you edit it.

  4. If your hosts pull images through an internal registry, copy the new image into it, then use your registry's image name in the commands on this page:

    docker pull newrelic/network-agent:latest
docker tag newrelic/network-agent:latest $YOUR_REGISTRY/newrelic/network-agent:latest
docker push $YOUR_REGISTRY/newrelic/network-agent:latest
tip

Migrate one container first and check that it reports all its devices before you migrate the rest. Each container stops sending data for a minute or two while you switch it over.

Migrate a Docker deployment

Repeat these steps for each container:

  1. Pull the new image. Pulling it while the old container still runs keeps the gap in your data short:

    docker pull newrelic/network-agent:latest

  2. Stop the old container:

    docker stop ktranslate-$CONTAINER_SERVICE

    If the old container's restart policy is always, also turn it off so the container doesn't start again when Docker or the host restarts:

    docker update --restart=no ktranslate-$CONTAINER_SERVICE

  3. In the container's snmp-base.yaml file, update the two paths under global:

    global:
  mib_profile_dir: /etc/network-agent/profiles
  mibs_db: /etc/network-agent/mibs.db

    If your file doesn't have a mibs_db line, update mib_profile_dir only.

    Change the file only after you stop the old container. kTranslate can't use the new paths, so if the old container restarted with them, it would keep restarting.

    important

    Don't skip this step, even for flow and syslog containers. With the old /etc/ktranslate paths, the New Relic Network Agent can't load its SNMP profiles, so the container stops right after it starts and keeps restarting.

  4. Start the new container with your original docker run command, changing the container name and the image. If any flag or mount in the command uses a path under /etc/ktranslate, such as -mapping /etc/ktranslate/config.json, change it to the same path under /etc/network-agent. Keep the same -service_name value: it sets the tags.container_service attribute on your data, so anything filtered on it keeps working. For example, for SNMP polling:

    docker run -d --name network-agent-$CONTAINER_SERVICE \
  --restart unless-stopped --pull=always -p 162:1620/udp \
  -v `pwd`/snmp-base.yaml:/snmp-base.yaml \
  -e NEW_RELIC_API_KEY=$YOUR_NR_LICENSE_KEY \
  newrelic/network-agent:latest \
  -snmp /snmp-base.yaml \
  -nr_account_id=$YOUR_NR_ACCOUNT_ID \
  -metrics=jchf \
  -tee_logs=true \
  -service_name=$CONTAINER_SERVICE \
  -snmp_discovery_on_start=true \
  -snmp_discovery_min=180 \
  nr1.snmp

    For commands for each type of container, see Example commands.

  5. Check that the new container started:

    docker logs network-agent-$CONTAINER_SERVICE 2>&1 | grep "Running --"

    You should see a line like NetworkAgent Running -- version X.Y.Z. Within a few minutes, the container also appears as network-agent in the migration tracking query.

  6. Check that the new container reports every device the old one did. Wait at least two polling intervals after it starts (global.poll_time_sec in snmp-base.yaml), then run this query in New Relic. Replace YOUR_CONTAINER_SERVICE with the container's -service_name value, and make sure the time window starts before you stopped the old container:

    FROM Metric
SELECT filter(count(*), WHERE collector.name = 'ktranslate') AS 'kTranslate',
  filter(count(*), WHERE collector.name = 'network-agent') AS 'New Relic Network Agent'
WHERE instrumentation.provider = 'kentik'
AND tags.container_service = 'YOUR_CONTAINER_SERVICE'
AND provider != 'kentik-agent'
FACET device_name
SINCE 3 hours ago
LIMIT MAX

    Each row is one device, with the number of data points each agent sent for it. Every device that has data under kTranslate should also have data under New Relic Network Agent. A 0 under New Relic Network Agent means the new container isn't reporting that device yet. If your container doesn't use -service_name, leave out the tags.container_service line; the query then covers all your containers. The provider line leaves out the agent's own health metrics, which would otherwise show the old container as a missing device.

    For other types of containers, change the query:

    • Network flow: use FROM KFlow instead of FROM Metric, and leave out the provider line.
    • Syslog: use FROM Log, replace the tags.container_service line with AND plugin.type = 'ktranslate-syslog', and leave out the provider line. This version covers all your syslog containers together.

    If a device is missing, look for errors that mention it in the container logs. For SNMP, also check that the device is still listed under devices in snmp-base.yaml.

    docker logs network-agent-$CONTAINER_SERVICE 2>&1 | grep "$DEVICE_NAME"

  7. When the new container reports all its devices, remove the old one:

    docker rm ktranslate-$CONTAINER_SERVICE
tip

Until you remove the old container, you can roll back: stop the new container, restore your backed-up snmp-base.yaml, and run docker start ktranslate-$CONTAINER_SERVICE. If you turned off the old container's restart policy, turn it back on with docker update --restart=unless-stopped ktranslate-$CONTAINER_SERVICE.

If you mount custom SNMP profiles

If you mount your own SNMP profiles into the container, change the mount target to the new profile folder. It must match the mib_profile_dir value you set in step 3:

-v `pwd`/snmp-profiles/profiles:/etc/network-agent/profiles

If you deploy with Docker Compose, Kubernetes, or scripts

Make the same changes in your deployment files, then redeploy so that each container is re-created:

  • Change the image from kentik/ktranslate:v2, or any version tag you pinned, to newrelic/network-agent:latest.
  • Update the two paths in the snmp-base.yaml file you deploy, as described in step 3.
  • Change any mount target or flag path under /etc/ktranslate, such as custom profiles, to the same path under /etc/network-agent.
  • Keep your flags and environment variables as they are.

For example, in a Docker Compose file:

services:
  network-agent-snmp:
    image: newrelic/network-agent:latest  # was kentik/ktranslate:v2
    volumes:
      - ./snmp-base.yaml:/snmp-base.yaml
    # Keep your existing command, ports, and environment settings.

Get newer versions

The New Relic Network Agent doesn't update itself. With the latest tag, a container picks up a newer version when you re-create it, because --pull=always pulls the newest image when the container is created. Restarting an existing container keeps the version it already has.

To move a container to the newest version, remove it and run your docker run command again:

docker rm -f network-agent-$CONTAINER_SERVICE

To run a specific version instead, replace latest with a version tag from Docker Hub, for example newrelic/network-agent:$VERSION. The kTranslate version tags, such as kt-2023-02-28-4294815650, don't apply to the new image.

Move from Podman or a Linux package to Docker

caution

Podman and Linux package installations aren't supported with the New Relic Network Agent. Move these deployments to Docker.

You can keep your existing snmp-base.yaml files and settings. Install Docker on the host, then follow the steps for your current setup:

From Podman

  1. List your kTranslate containers:

    podman ps -a --format "{{.ID}}  {{.Names}}  {{.Image}}" | grep ktranslate

  2. Note each container's flags, environment variables, mounted files, and ports. podman inspect accepts the same --format options shown in Before you begin.

  3. Stop the Podman container. If a systemd unit starts it automatically, disable that unit too.

    podman stop $CONTAINER_NAME

  4. In the container's snmp-base.yaml file, update the two paths under global, as described in step 3 of the Docker migration.

  5. Start the container with Docker, using the matching command from Example commands and the same flags and files you noted in step 2.

  6. When the new container reports all its devices (see step 6 of the Docker migration), remove the Podman container:

    podman rm $CONTAINER_NAME
From a Linux package

Your current settings are in two files:

  • /etc/ktranslate/snmp-base.yaml: your devices and discovery settings
  • /etc/default/ktranslate.env: your account ID, license key, and the agent flags in KT_FLAGS

  1. Copy your configuration file to a working folder and give ownership to user ID 1000, which the container runs as:

    mkdir -p ~/network-agent && cd ~/network-agent
sudo cp /etc/ktranslate/snmp-base.yaml .
sudo chown 1000:1000 snmp-base.yaml

    If you customized profiles in /etc/ktranslate/profiles, copy that folder too and mount it as described in If you mount custom SNMP profiles.

  2. Edit the copy:

    • Update the two paths under global, as described in step 3 of the Docker migration.
    • If the agent receives SNMP traps, change trap.listen from 0.0.0.0:162 to 0.0.0.0:1620. Docker publishes host port 162 to this port.

  3. Build your docker run command from the matching command in Example commands:

    • Use the NR_ACCOUNT_ID and NEW_RELIC_API_KEY values from /etc/default/ktranslate.env.
    • Add any other flags from KT_FLAGS that the command doesn't already include.
    • If one of those flags points to a file under /etc/ktranslate, copy the file to your working folder, mount it into the container under /etc/network-agent, and point the flag at that path.
    • For syslog, leave out -syslog.source=0.0.0.0:514. The container listens on port 5143, and -p 514:5143/udp publishes it on host port 514.

  4. Stop and disable the kTranslate service so that it releases its ports:

    sudo systemctl disable --now ktranslate

  5. From the folder that holds your snmp-base.yaml, run your docker run command.

  6. When the new container reports all its devices (see step 6 of the Docker migration), uninstall the package:

    # Yum
sudo yum remove ktranslate
# Apt
sudo apt-get remove ktranslate

    Until you uninstall the package, you can roll back: stop the container and run sudo systemctl enable --now ktranslate.

Find the agent's logs

The New Relic Network Agent writes its logs to the container's output. To read them, run:

docker logs network-agent-$CONTAINER_SERVICE

If the container runs with -tee_logs=true, as in the example commands, the agent also sends these logs to New Relic Logs.

Compared with kTranslate, the logs change in these ways:

  • Each line names the agent as network-agent/ followed by your -service_name value, instead of ktranslate/.
  • The agent's own messages, such as the startup line, start with NetworkAgent instead of KTranslate.
  • In New Relic Logs, collector.name is network-agent instead of ktranslate.

The logtype and plugin.type attributes stay ktranslate-health, so log searches and alerts that filter on them keep working.

For example, for a container with -service_name=snmp, this kTranslate startup line:

2021-12-06T22:30:01.123+00:00 ktranslate/snmp [Info] KTranslate Running -- Version kt-2021-12-06-1546870234; Build Mon Dec  6 22:22:56 UTC 2021

looks like this in the New Relic Network Agent:

2026-11-03T10:15:02.123+00:00 network-agent/snmp [Info] NetworkAgent Running -- version X.Y.Z

Update queries, alerts, and dashboards

Device metrics and entities don't change, so dashboards and alerts built on them keep working. Update anything that identifies the agent itself, such as the queries in Docker container health monitoring:

  • collector.name: change 'ktranslate' to 'network-agent'. In the logs search bar, use collector.name:"network-agent".
  • Agent log text: the message prefix changes from KTranslate to NetworkAgent, as described in Find the agent's logs.

While you migrate, some of your containers still run kTranslate. To cover both agents, match either value:

FROM Log SELECT *
WHERE collector.name IN ('ktranslate', 'network-agent')
AND message LIKE '%Running --%'

This query finds the startup line from both agents: kTranslate writes Version and the New Relic Network Agent writes version, and both lines contain Running --. Check your NRQL alert conditions and dashboard widgets for the same values.

Track your migration

To see which of your containers already run the New Relic Network Agent, run this query. Rows that show ktranslate in the Agent column still need to be migrated.

FROM Metric
SELECT latest(ver) AS 'Version'
FACET collector.name AS 'Agent', host AS 'Host', svc AS 'Container service'
WHERE provider = 'kentik-agent'
AND instrumentation.name = 'heartbeat'
SINCE 1 hour ago

A container you've migrated shows up with network-agent a few minutes after it starts. Its old ktranslate row drops off when the query's time window no longer includes data from the old container.

Troubleshooting

The new container keeps restarting

The container logs show an error like There was an error when setting up the /etc/ktranslate/mibs.db mibDB database and the /etc/ktranslate/profiles profiles. Your snmp-base.yaml still has the old paths.

Update the paths as described in step 3 of the Docker migration, then re-create the container: run docker rm -f network-agent-$CONTAINER_SERVICE, then your docker run command.

docker run fails because the container name is already in use

Another container already has that name, for example from an earlier attempt. Remove it with docker rm -f $CONTAINER_NAME, or choose a different name.

docker run fails because a port is already allocated or in use

Something still holds port 162 (traps) or 514 (syslog), usually the old kTranslate container or service. Stop it first:

  • Docker: docker stop ktranslate-$CONTAINER_SERVICE
  • Podman: podman stop $CONTAINER_NAME
  • Linux package: sudo systemctl disable --now ktranslate
SNMP traps stop arriving after moving from a Linux package

Inside the container, the agent listens for traps on port 1620. In your snmp-base.yaml, set trap.listen to 0.0.0.0:1620, and publish the port with -p 162:1620/udp.

Discovery fails with a permissions error

The container runs as user ID 1000 and needs to write to snmp-base.yaml. Run sudo chown 1000:1000 snmp-base.yaml. For more details, see The container is running but discovery job doesn't begin.

Health queries or alerts show no data after migrating

They still filter on collector.name = 'ktranslate' or on KTranslate log text. Update them as described in Update queries, alerts, and dashboards.

A container still runs an older version

Restarting a container doesn't pull a newer image. Re-create the container as described in Get newer versions.

Only queries that filter on `collector.name` or on agent log text need updates. For details, see [Update queries, alerts, and dashboards](#update-queries).

## Before you begin [#before-you-begin]

1. On each Docker host, list your kTranslate containers:

   ```shell
   docker ps -a --format "{{.ID}}  {{.Names}}  {{.Image}}" | grep ktranslate
   ```

   Output example:

   ```
   3297b134a352  ktranslate-snmp   kentik/ktranslate:v2
   4962a854b386  ktranslate-sflow  kentik/ktranslate:v2
   ```

2. Note the settings each container was started with. If you no longer have the original `docker run` command, `docker inspect` shows them:

   ```shell
   # Flags passed after the image name
   docker inspect --format '{{json .Config.Cmd}}' $CONTAINER_NAME
   # Environment variables (this includes your license key, so don't share the output)
   docker inspect --format '{{json .Config.Env}}' $CONTAINER_NAME
   # Files mounted into the container, such as snmp-base.yaml
   docker inspect --format '{{json .HostConfig.Binds}}' $CONTAINER_NAME
   # Published ports, network mode, and restart policy
   docker inspect --format '{{json .HostConfig.PortBindings}} {{.HostConfig.NetworkMode}} {{.HostConfig.RestartPolicy.Name}}' $CONTAINER_NAME
   ```

3. Back up each `snmp-base.yaml` file before you edit it.

4. If your hosts pull images through an internal registry, copy the new image into it, then use your registry's image name in the commands on this page:

   ```shell
   docker pull newrelic/network-agent:latest
   docker tag newrelic/network-agent:latest $YOUR_REGISTRY/newrelic/network-agent:latest
   docker push $YOUR_REGISTRY/newrelic/network-agent:latest
   ```

<Callout variant="tip">
  Migrate one container first and check that it reports all its devices before you migrate the rest. Each container stops sending data for a minute or two while you switch it over.
</Callout>

## Migrate a Docker deployment [#migrate-docker]

Repeat these steps for each container:

1. Pull the new image. Pulling it while the old container still runs keeps the gap in your data short:

   ```shell
   docker pull newrelic/network-agent:latest
   ```

2. Stop the old container:

   ```shell
   docker stop ktranslate-$CONTAINER_SERVICE
   ```

   If the old container's restart policy is `always`, also turn it off so the container doesn't start again when Docker or the host restarts:

   ```shell
   docker update --restart=no ktranslate-$CONTAINER_SERVICE
   ```

3. In the container's `snmp-base.yaml` file, update the two paths under `global`:

   ```yaml
   global:
     mib_profile_dir: /etc/network-agent/profiles
     mibs_db: /etc/network-agent/mibs.db
   ```

   If your file doesn't have a `mibs_db` line, update `mib_profile_dir` only.

   Change the file only after you stop the old container. kTranslate can't use the new paths, so if the old container restarted with them, it would keep restarting.

   <Callout variant="important">
     Don't skip this step, even for flow and syslog containers. With the old `/etc/ktranslate` paths, the New Relic Network Agent can't load its SNMP profiles, so the container stops right after it starts and keeps restarting.
   </Callout>

4. Start the new container with your original `docker run` command, changing the container name and the image. If any flag or mount in the command uses a path under `/etc/ktranslate`, such as `-mapping /etc/ktranslate/config.json`, change it to the same path under `/etc/network-agent`. Keep the same `-service_name` value: it sets the `tags.container_service` attribute on your data, so anything filtered on it keeps working. For example, for SNMP polling:

   ```shell
   docker run -d --name network-agent-$CONTAINER_SERVICE \
     --restart unless-stopped --pull=always -p 162:1620/udp \
     -v `pwd`/snmp-base.yaml:/snmp-base.yaml \
     -e NEW_RELIC_API_KEY=$YOUR_NR_LICENSE_KEY \
     newrelic/network-agent:latest \
     -snmp /snmp-base.yaml \
     -nr_account_id=$YOUR_NR_ACCOUNT_ID \
     -metrics=jchf \
     -tee_logs=true \
     -service_name=$CONTAINER_SERVICE \
     -snmp_discovery_on_start=true \
     -snmp_discovery_min=180 \
     nr1.snmp
   ```

   For commands for each type of container, see [Example commands](#example-commands).

5. Check that the new container started:

   ```shell
   docker logs network-agent-$CONTAINER_SERVICE 2>&1 | grep "Running --"
   ```

   You should see a line like `NetworkAgent Running -- version X.Y.Z`. Within a few minutes, the container also appears as `network-agent` in the [migration tracking query](#track-migration).

6. Check that the new container reports every device the old one did. Wait at least two polling intervals after it starts (`global.poll_time_sec` in `snmp-base.yaml`), then run this query in New Relic. Replace `YOUR_CONTAINER_SERVICE` with the container's `-service_name` value, and make sure the time window starts before you stopped the old container:

   ```sql
   FROM Metric
   SELECT filter(count(*), WHERE collector.name = 'ktranslate') AS 'kTranslate',
     filter(count(*), WHERE collector.name = 'network-agent') AS 'New Relic Network Agent'
   WHERE instrumentation.provider = 'kentik'
   AND tags.container_service = 'YOUR_CONTAINER_SERVICE'
   AND provider != 'kentik-agent'
   FACET device_name
   SINCE 3 hours ago
   LIMIT MAX
   ```

   Each row is one device, with the number of data points each agent sent for it. Every device that has data under **kTranslate** should also have data under **New Relic Network Agent**. A `0` under **New Relic Network Agent** means the new container isn't reporting that device yet. If your container doesn't use `-service_name`, leave out the `tags.container_service` line; the query then covers all your containers. The `provider` line leaves out the agent's own health metrics, which would otherwise show the old container as a missing device.

   For other types of containers, change the query:

   * **Network flow:** use `FROM KFlow` instead of `FROM Metric`, and leave out the `provider` line.
   * **Syslog:** use `FROM Log`, replace the `tags.container_service` line with `AND plugin.type = 'ktranslate-syslog'`, and leave out the `provider` line. This version covers all your syslog containers together.

   If a device is missing, look for errors that mention it in the container logs. For SNMP, also check that the device is still listed under `devices` in `snmp-base.yaml`.

   ```shell
   docker logs network-agent-$CONTAINER_SERVICE 2>&1 | grep "$DEVICE_NAME"
   ```

7. When the new container reports all its devices, remove the old one:

   ```shell
   docker rm ktranslate-$CONTAINER_SERVICE
   ```

<Callout variant="tip">
  Until you remove the old container, you can roll back: stop the new container, restore your backed-up `snmp-base.yaml`, and run `docker start ktranslate-$CONTAINER_SERVICE`. If you turned off the old container's restart policy, turn it back on with `docker update --restart=unless-stopped ktranslate-$CONTAINER_SERVICE`.
</Callout>

### If you mount custom SNMP profiles [#custom-profiles]

If you mount your own SNMP profiles into the container, change the mount target to the new profile folder. It must match the `mib_profile_dir` value you set in step 3:

```shell
-v `pwd`/snmp-profiles/profiles:/etc/network-agent/profiles
```

### If you deploy with Docker Compose, Kubernetes, or scripts [#deployment-pipelines]

Make the same changes in your deployment files, then redeploy so that each container is re-created:

* Change the image from `kentik/ktranslate:v2`, or any version tag you pinned, to `newrelic/network-agent:latest`.
* Update the two paths in the `snmp-base.yaml` file you deploy, as described in step 3.
* Change any mount target or flag path under `/etc/ktranslate`, such as custom profiles, to the same path under `/etc/network-agent`.
* Keep your flags and environment variables as they are.

For example, in a Docker Compose file:

```yaml
services:
  network-agent-snmp:
    image: newrelic/network-agent:latest  # was kentik/ktranslate:v2
    volumes:
      - ./snmp-base.yaml:/snmp-base.yaml
    # Keep your existing command, ports, and environment settings.
```

### Get newer versions [#newer-versions]

The New Relic Network Agent doesn't update itself. With the `latest` tag, a container picks up a newer version when you re-create it, because `--pull=always` pulls the newest image when the container is created. Restarting an existing container keeps the version it already has.

To move a container to the newest version, remove it and run your `docker run` command again:

```shell
docker rm -f network-agent-$CONTAINER_SERVICE
```

To run a specific version instead, replace `latest` with a version tag from [Docker Hub](https://hub.docker.com/r/newrelic/network-agent/tags), for example `newrelic/network-agent:$VERSION`. The kTranslate version tags, such as `kt-2023-02-28-4294815650`, don't apply to the new image.

## Move from Podman or a Linux package to Docker [#move-to-docker]

<Callout variant="caution">
  Podman and Linux package installations aren't supported with the New Relic Network Agent. Move these deployments to Docker.
</Callout>

You can keep your existing `snmp-base.yaml` files and settings. [Install Docker](https://docs.docker.com/engine/install/) on the host, then follow the steps for your current setup:

<CollapserGroup>
  <Collapser
    id="from-podman"
    title="From Podman"
  >
    1. List your kTranslate containers:

       ```shell
       podman ps -a --format "{{.ID}}  {{.Names}}  {{.Image}}" | grep ktranslate
       ```

    2. Note each container's flags, environment variables, mounted files, and ports. `podman inspect` accepts the same `--format` options shown in [Before you begin](#before-you-begin).

    3. Stop the Podman container. If a systemd unit starts it automatically, disable that unit too.

       ```shell
       podman stop $CONTAINER_NAME
       ```

    4. In the container's `snmp-base.yaml` file, update the two paths under `global`, as described in [step 3 of the Docker migration](#migrate-docker).

    5. Start the container with Docker, using the matching command from [Example commands](#example-commands) and the same flags and files you noted in step 2.

    6. When the new container reports all its devices (see [step 6 of the Docker migration](#migrate-docker)), remove the Podman container:

       ```shell
       podman rm $CONTAINER_NAME
       ```
  </Collapser>

  <Collapser
    id="from-linux-package"
    title="From a Linux package"
  >
    Your current settings are in two files:

    * `/etc/ktranslate/snmp-base.yaml`: your devices and discovery settings
    * `/etc/default/ktranslate.env`: your account ID, license key, and the agent flags in `KT_FLAGS`

    1. Copy your configuration file to a working folder and give ownership to user ID 1000, which the container runs as:

       ```shell
       mkdir -p ~/network-agent && cd ~/network-agent
       sudo cp /etc/ktranslate/snmp-base.yaml .
       sudo chown 1000:1000 snmp-base.yaml
       ```

       If you customized profiles in `/etc/ktranslate/profiles`, copy that folder too and mount it as described in [If you mount custom SNMP profiles](#custom-profiles).

    2. Edit the copy:

       * Update the two paths under `global`, as described in [step 3 of the Docker migration](#migrate-docker).
       * If the agent receives SNMP traps, change `trap.listen` from `0.0.0.0:162` to `0.0.0.0:1620`. Docker publishes host port 162 to this port.

    3. Build your `docker run` command from the matching command in [Example commands](#example-commands):

       * Use the `NR_ACCOUNT_ID` and `NEW_RELIC_API_KEY` values from `/etc/default/ktranslate.env`.
       * Add any other flags from `KT_FLAGS` that the command doesn't already include.
       * If one of those flags points to a file under `/etc/ktranslate`, copy the file to your working folder, mount it into the container under `/etc/network-agent`, and point the flag at that path.
       * For syslog, leave out `-syslog.source=0.0.0.0:514`. The container listens on port 5143, and `-p 514:5143/udp` publishes it on host port 514.

    4. Stop and disable the kTranslate service so that it releases its ports:

       ```shell
       sudo systemctl disable --now ktranslate
       ```

    5. From the folder that holds your `snmp-base.yaml`, run your `docker run` command.

    6. When the new container reports all its devices (see [step 6 of the Docker migration](#migrate-docker)), uninstall the package:

       ```shell
       # Yum
       sudo yum remove ktranslate
       # Apt
       sudo apt-get remove ktranslate
       ```

    Until you uninstall the package, you can roll back: stop the container and run `sudo systemctl enable --now ktranslate`.
  </Collapser>
</CollapserGroup>

## Find the agent's logs [#agent-logs]

The New Relic Network Agent writes its logs to the container's output. To read them, run:

```shell
docker logs network-agent-$CONTAINER_SERVICE
```

If the container runs with `-tee_logs=true`, as in the example commands, the agent also sends these logs to [New Relic Logs](/docs/logs/ui-data/use-logs-ui).

Compared with kTranslate, the logs change in these ways:

* Each line names the agent as `network-agent/` followed by your `-service_name` value, instead of `ktranslate/`.
* The agent's own messages, such as the startup line, start with `NetworkAgent` instead of `KTranslate`.
* In New Relic Logs, `collector.name` is `network-agent` instead of `ktranslate`.

The `logtype` and `plugin.type` attributes stay `ktranslate-health`, so log searches and alerts that filter on them keep working.

For example, for a container with `-service_name=snmp`, this kTranslate startup line:

```
2021-12-06T22:30:01.123+00:00 ktranslate/snmp [Info] KTranslate Running -- Version kt-2021-12-06-1546870234; Build Mon Dec  6 22:22:56 UTC 2021
```

looks like this in the New Relic Network Agent:

```
2026-11-03T10:15:02.123+00:00 network-agent/snmp [Info] NetworkAgent Running -- version X.Y.Z
```

## Update queries, alerts, and dashboards [#update-queries]

Device metrics and entities don't change, so dashboards and alerts built on them keep working. Update anything that identifies the agent itself, such as the queries in [Docker container health monitoring](/docs/network-performance-monitoring/advanced/network-agent-container-health):

* **`collector.name`:** change `'ktranslate'` to `'network-agent'`. In the logs search bar, use `collector.name:"network-agent"`.
* **Agent log text:** the message prefix changes from `KTranslate` to `NetworkAgent`, as described in [Find the agent's logs](#agent-logs).

While you migrate, some of your containers still run kTranslate. To cover both agents, match either value:

```sql
FROM Log SELECT *
WHERE collector.name IN ('ktranslate', 'network-agent')
AND message LIKE '%Running --%'
```

This query finds the startup line from both agents: kTranslate writes `Version` and the New Relic Network Agent writes `version`, and both lines contain `Running --`. Check your NRQL alert conditions and dashboard widgets for the same values.

## Track your migration [#track-migration]

To see which of your containers already run the New Relic Network Agent, run this query. Rows that show `ktranslate` in the **Agent** column still need to be migrated.

```sql
FROM Metric
SELECT latest(ver) AS 'Version'
FACET collector.name AS 'Agent', host AS 'Host', svc AS 'Container service'
WHERE provider = 'kentik-agent'
AND instrumentation.name = 'heartbeat'
SINCE 1 hour ago
```

A container you've migrated shows up with `network-agent` a few minutes after it starts. Its old `ktranslate` row drops off when the query's time window no longer includes data from the old container.

## Troubleshooting [#troubleshooting]

<CollapserGroup>
  <Collapser
    id="container-keeps-restarting"
    title="The new container keeps restarting"
  >
    The container logs show an error like `There was an error when setting up the /etc/ktranslate/mibs.db mibDB database and the /etc/ktranslate/profiles profiles`. Your `snmp-base.yaml` still has the old paths.

    Update the paths as described in [step 3 of the Docker migration](#migrate-docker), then re-create the container: run `docker rm -f network-agent-$CONTAINER_SERVICE`, then your `docker run` command.
  </Collapser>

  <Collapser
    id="container-name-in-use"
    title="docker run fails because the container name is already in use"
  >
    Another container already has that name, for example from an earlier attempt. Remove it with `docker rm -f $CONTAINER_NAME`, or choose a different name.
  </Collapser>

  <Collapser
    id="port-in-use"
    title="docker run fails because a port is already allocated or in use"
  >
    Something still holds port 162 (traps) or 514 (syslog), usually the old kTranslate container or service. Stop it first:

    * Docker: `docker stop ktranslate-$CONTAINER_SERVICE`
    * Podman: `podman stop $CONTAINER_NAME`
    * Linux package: `sudo systemctl disable --now ktranslate`
  </Collapser>

  <Collapser
    id="traps-missing-after-linux"
    title="SNMP traps stop arriving after moving from a Linux package"
  >
    Inside the container, the agent listens for traps on port 1620. In your `snmp-base.yaml`, set `trap.listen` to `0.0.0.0:1620`, and publish the port with `-p 162:1620/udp`.
  </Collapser>

  <Collapser
    id="discovery-permission-error"
    title="Discovery fails with a permissions error"
  >
    The container runs as user ID 1000 and needs to write to `snmp-base.yaml`. Run `sudo chown 1000:1000 snmp-base.yaml`. For more details, see [The container is running but discovery job doesn't begin](/docs/network-performance-monitoring/troubleshooting/chtimes-error).
  </Collapser>

  <Collapser
    id="health-queries-empty"
    title="Health queries or alerts show no data after migrating"
  >
    They still filter on `collector.name = 'ktranslate'` or on `KTranslate` log text. Update them as described in [Update queries, alerts, and dashboards](#update-queries).
  </Collapser>

  <Collapser
    id="old-version-after-update"
    title="A container still runs an older version"
  >
    Restarting a container doesn't pull a newer image. Re-create the container as described in [Get newer versions](#newer-versions).
  </Collapser>
</CollapserGroup>
